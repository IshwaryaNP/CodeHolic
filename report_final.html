Architecture & Design

Bitcask Log-Structured Storage Model

Bitcask uses an append-only log for all writes. Every Put and Delete appends a fixed-header record to the data file. An in-memory hash index (KeyDir) maps each key to the latest record's file offset and length. On startup, the engine scans the log to rebuild the index — this is the recovery phase.

📐 Record Format on Disk
┌──────────────┬──────────────┬──────────────┬─────────────┬──────────────────────────────────┐
│  CRC32 (4B)  │ Timestamp(8B)│  KeyLen (2B) │  ValLen (4B)│  Key (≤1024B) + Value (≤1MB)     │
└──────────────┴──────────────┴──────────────┴─────────────┴──────────────────────────────────┘
Header = 18 bytes. CRC32 covers the entire record. A tombstone record has ValLen = 0xFFFFFFFF.

Key Design Decisions

🔒 Write-Ahead Logging
Every write is fsync'd before the in-memory index is updated, ensuring no data is acknowledged until it is durable on disk.
🔄 Append-Only Log
Writes never overwrite existing data. Old versions of keys remain on disk until compaction runs, enabling crash-safe recovery.
⚡ In-Memory Index
KeyDir is a map[string]IndexEntry held in RAM. Reads are O(1) in-memory lookup + single disk seek — no B-tree traversal needed.
🗜️ Compaction
Rewrites only the live (latest) version of each key to a new file. Atomic swap via rename. Writers are blocked while the new file is synced and renamed.

Implementation Steps (1 – 9)
59c222c
Step 1 — Disk Full Protection (--max-bytes)

Added ErrDiskFull sentinel error. The DB struct gained a maxBytes field (set via CLI flag --max-bytes). Before every write, the engine checks current file size + incoming record size + a 64 KB headroom. If the projected size exceeds the limit, the write returns ErrDiskFull immediately without touching the file. Delete operations are always allowed (they shrink space). Compaction is also allowed since it creates a temporary file and replaces the old one — net size reduction.

Files changed: src/db.go, src/ops.go, src/batch.go, src/record.go, cmd/kvdb/main.go, src/disk_full_test.go (75 lines of tests)
7570866
Step 2 — Write Rollback on Error (Truncate + fsync)

If a write fails mid-record (e.g., OS error, full disk mid-write), the engine calls Truncate to revert the file to its pre-write size, then calls Sync to durably persist the truncation. This prevents torn records from appearing as valid data during recovery. Added handleWriteFailure() helper in src/ops.go.

Also added src/batch_fail_test.go: 76 lines of tests that inject a mid-batch write failure using a fake writer, then verify the DB state is consistent after re-opening.

f32d8ff
Step 3 — Atomic Batch (ONE buffer, ONE write, ONE sync)

Rewrote Batch.Commit() to stage all operations into a single bytes.Buffer, issue one File.Write(), and one File.Sync(). This guarantees that a batch is either fully durable or fully absent — no partial batches on disk. Enforced spec limits: batch size ≤ 10,000 ops, key ≤ 1,024 B, value ≤ 1 MB. The batch fails atomically if any limit is exceeded.

0249d2d
Step 4 — Recovery Hardening

DecodeHeader in src/record.go now rejects any record where KeyLen > SpecMaxKeySize or ValLen > SpecMaxValueSize (treating them as corruption). The recovery scanner detects torn tail records and truncates+fsyncs the file at the last valid record boundary. Idempotent: re-opening after a crash is safe.

Performance benchmark: Recovery of 1,000,000 keys from disk completes in ~549ms — well under the 2-second spec limit.

247c937
Step 5 — Compaction (fsync + atomic rename)

Compaction now follows the full durability protocol: (1) write all live records to data.tmp, (2) fsync the tmp file, (3) close it, (4) rename it over data.db (atomic on POSIX; near-atomic on Windows), (5) fsync the directory (skipped on Windows — guarded by runtime.GOOS != "windows"). Writers acquire an exclusive lock during rename. Stale .tmp files from previous failed compactions are cleaned up on startup.

Added TestCompactionShrinks to src/recovery_compaction_test.go to verify the data file is smaller after compaction.

930a705
Step 6 — Bulk Import (CLI, Library, Serve Mode, Web UI)

Added a full bulk-import pipeline:

  • src/bulk_import.go (365 lines): db.BulkImport() library accepting plain-text lines, csv, and jsonl formats. Processes data in configurable chunk sizes. Resumable via StartLine parameter. Streams from io.Reader — no full-file buffering. Each chunk is committed as one atomic batch.
  • CLI: kvdb import <file> [--format lines|csv|jsonl] [--chunk 500]
  • Serve mode: POST /import endpoint with multipart upload
  • Web UI panel: Drag-and-drop import with format selection, chunk-size control, and SSE-based live progress bar

4 Torture oracle false positive: "durability violation (Rule 1)" In-flight tracking used a single string per key; concurrent writers for the same key caused false mismatches when the second writer's value was checked against the first Changed inFlight map[string]string → map[string]map[string]bool (per-key multi-value set)

7 UI server bind: forbidden access permissions on port 8080 Port 8080 in use by another process on the machine Use --addr 127.0.0.1:8081 or any free port above 8080
8 handleWriteFailure did not fsync after Truncate Missing Sync() call after Truncate() — the truncation itself could be lost on a subsequent crash Added file.Sync() immediately after file.Truncate() in src/ops.go
